# AGENTS.md

This repository is faker-kit, a kit of agent skills for Claude Code. Read [README.md](README.md) for what it offers. This file tells an agent how to change it.

## Layout

- `plugins/<name>/` for every name in `upstream/source.json`: vendored from the upstream repository in `upstream/source.json`. Byte-identical to upstream except the rules in `upstream/model-map.json`, `upstream/compat-patches.json`, and `upstream/renames.json`, plus generated `.claude-plugin/plugin.json` and `agent-hooks/` files. A plugin named in `pluginSources` in `upstream/source.json` is read from that subdirectory instead of its own folder; pstack comes from upstream's generated Claude Code build, `harness/pstack/claude-code/`, so rules name its files by that path.
- `upstream/agent-hooks/hook-adapter.mjs`: runs a vendored plugin's upstream hooks from Claude Code hooks. The sync script copies it into each plugin that has a `hooks/hooks.json`.
- `plugins/trust-ladder/`: this repo's own plugin. Skills, templates, and helper scripts.
- `hermes/`: the Hermes module, this repo's own. The bootstrap, project, and chief bots' skills, profiles, guard plugin, the one `faker-kit` command, scheduled jobs, and `install.sh`. It loads only in Hermes bots, never in a coding agent, so it is not a plugin. Its skills follow the trust-ladder naming rules but need no `docs/catalog.json` entry, and must not reuse a plugin skill's name. See `hermes/README.md`.
- `docs/`: the kit's own pages (install, set up a repository, roll out, correct an agent, Hermes dispatch, the trust ladder, engineers' start page). `docs/README.md` indexes them and links into the vendored pstack guide (`plugins/pstack/docs/guide/`) and the plugin READMEs instead of restating them. `docs/reference/skills.md` is generated from `docs/catalog.json` and each SKILL.md.
- `scripts/`: `sync-upstream.mjs`, `validate.mjs`, and the generators and test runners.

## Never edit vendored files by hand

A hand edit under a vendored plugin fails `node scripts/sync-upstream.mjs --check`. To change a vendored file:

1. Model names: add or adjust a rule in `upstream/model-map.json`. Set `count` to the exact number of replacements.
2. A file that cannot load in Claude Code without an edit: add a rule to `upstream/compat-patches.json` (same shape) and say why in the rule id.
3. A name the team chose over upstream's: add a path or text rule to `upstream/renames.json`.
4. An upstream hook event the adapter does not map yet: add it to `UPSTREAM_TO_AGENT_EVENT` in the sync script and to the adapter, with a step in `scripts/e2e/kit-e2e.mjs` that runs the adapter on that event.
5. Anything else: change the behavior in `plugins/trust-ladder/` (a wrapper skill, hook, or template), not in the vendored file.
6. Run `node scripts/sync-upstream.mjs --src <checkout of the upstream repository>` or without `--src` to clone it.

To take a newer upstream: `node scripts/sync-upstream.mjs --ref <sha>`. Fix any rule whose count changed, then read `upstream/CHANGES.md` in the diff.

## Writing trust-ladder skills

- `name` equals the directory name: lowercase letters, digits, single hyphens.
- `description` says what the skill does and when to use it, in under 1024 characters.
- Write for an agent reading the file cold. Say which tool does what using the vocabulary in `plugins/trust-ladder/references/compat.md`.
- Never reuse a vendored skill's name. A project links skills by bare name, so a repeated name collides.
- If a vendored skill already covers the capability, use it (wrap it if the team needs more) instead of writing a second trust-ladder skill.
- Add every new skill to `docs/catalog.json` (layer, audience, an example prompt), then run `node scripts/gen-catalog.mjs`. `validate.mjs` fails on a skill without an entry.

## Checks

There is no single check command. CI runs these jobs in parallel (`.github/workflows/ci.yml`), and the commands below are the whole list:

| CI job | Commands |
|---|---|
| `lint` | `node scripts/agent-checks/ratchet.mjs check`, `node scripts/agent-checks/import-boundaries.mjs`, `node scripts/agent-checks/rule-fixtures.mjs`, `ruff check`, `mypy` |
| `validate` | `node scripts/sync-upstream.mjs --check`, `node scripts/validate.mjs`, `node scripts/gen-catalog.mjs --check` |
| `commit-messages` | `node scripts/check-commit-messages.mjs` |
| `hermes-e2e` | `python3 hermes/e2e/run_dispatch_e2e.py --artifact artifacts/hermes-e2e.json` |
| `agents-load-the-kit` | `claude plugin validate .`, `node scripts/e2e/kit-e2e.mjs --artifact artifacts/kit-e2e.json` |

The tools are `node`, `bun`, `jq`, `git`, `python3`, and `pip install ruff mypy types-PyYAML pyyaml`. Run the commands your change can affect, and `git add` new files first because the ratchet counts only tracked files:

- `hermes/` or `.agents/dispatch*`: `hermes-e2e`, then `lint`.
- `plugins/trust-ladder/`, `scripts/`, `docs/`, `upstream/`: `validate`, `kit-e2e`, then `lint`.
- A commit: `check-commit-messages`.

Each e2e run writes a JSON transcript to `artifacts/` and prints a digest that is the same on every run.

The kit has no unit tests. Prove behavior with the e2e runs: add a step that drives the real entry point (a hook, a script, the `faker-kit` command, the guard plugin loaded as Hermes loads it) and records what it observed; never import internals and assert on them. The only other proof is `.agents/rule-fixtures.json` (real linters on good and bad inputs).

CI also runs what needs other toolchains, which a cloud session may lack:

```bash
claude plugin validate .                 # Claude Code marketplace schema
```

The commands above prove the code passes; the `verify-faker-kit` skill proves a user gets the behavior. Run the ones your change affects and the skill before reporting a change done.

## Hermes invariants

- A project bot is the long-lived coordinator chat for one repository. It decides what to launch and when to merge; no code state machine chooses for it. Code keeps only these gates: the guard's hard blocks (secret reads, repository deletion, push to main or force-push, raw `gh pr merge` and the merge API, wiping / or home, edits to the kit and the guard's own files), and `faker-kit merge` as the only way to land a pull request. Its gate is code: every check on the head passed and at least one check run that succeeded on it belongs to a `push` or `pull_request` workflow run of this head (a `pull_request` run must come from this pull request's branch in this repository, start after the pull request opened, and be attached to this pull request and its base branch, a `push` run must come from this repository and counts only when the head's `.github/workflows` folder equals the default branch's, and no pull request from that branch, in any state, may ever have targeted another base, and this pull request's base was never changed) of a workflow other than the review workflow and the kit-checks workflow (the repository's own GitHub Actions CI that builds and tests the pull request), no person has requested changes, the pull request is open, from this repository, against the default branch, and free of conflicts, and the merge is pinned to the head it checked. Runs, jobs, check runs, and statuses of the review workflow are ignored: they neither pass nor block a merge, and no review, `Risk:` rating, or verdict is read. The `--owner-approved` flag stays on the command for the owner's request; the bot merges only when the owner asked, and no code checks that. With the flag the merge goes ahead over pending checks, failed checks, a failed or missing CI run, and a repository with no CI workflow, still pinned to the exact head, and prints each bypassed gate (each failed or pending check by name, and "no CI") in `bypassed`; it still refuses the andon cord, a conflict, a pull request that is not open, from this repository, and against the default branch, a person's requested changes, and the branch and base evidence checks, and its refusals say what to do next. An approval covers only the message that gave it; nothing stores it. `--wait <seconds>` (0 to 1800, default 0) waits inside the same call, polling every 30 seconds with fresh evidence, only while the head's checks are pending and none failed (with `--owner-approved` too: it waits first, then bypasses what is left); a failed check ends it at once, a head that moved refuses it, and the bound passing with checks still pending refuses with the time waited. The owner never retypes numbers: `--open` (every open non-draft pull request of one project), `--all-projects` (the chief only, every project on the machine) and `--match <text>` (open non-draft pull requests whose title or branch has the text) choose the targets, but only among pull requests opened by the GitHub login this machine's `gh` is signed in as (read once per call with `gh api user`, compared case-insensitively; unreadable refuses and merges nothing); another author's pull request is never merged by them and is listed under `skipped_not_owner` (`project`, `number`, `title`, `author`), `--match` counts only the machine login's candidates, and a call with no eligible pull request exits non-zero; `--pr N` merges whoever the author is and adds `author` and `named_by_owner` when it is not the machine login, run only with `--owner-approved`, are refused with `--pr` and without the flag, and send each pull request through the same `land` gate in ascending order; `--wait` defaults to 600 seconds there, shared by the whole call (a pull request the budget does not reach is reported `not attempted`), and several `--match` candidates merge nothing and exit 3 with `ambiguous`; `--pr N` is never replaced. `faker-kit launch` also refuses while the andon cord is pulled. The andon stop rule is an instruction in the skills, not code. A project bot clears its own cord, and acts on owner decisions on its project, only on the owner's own words: their message in the bot's own chat, or a message from the chief bot carrying a line starting `Owner said (verbatim):` with the owner's message copied unchanged, which the bot copies into its store, checks against the cord's reason, and answers with the cord read back; no relay is merge approval, releases an owner-merge-only, draft-only, or other hold, launches work the owner did not decide, or touches another project's cord, and the chief never clears or pulls a cord. No separate session checks a pull request before a merge: a bot lands a pull request through `faker-kit merge` when the owner asks or when its gates pass, and the author's own session may run the project's verification skills. `faker-kit status` and `faker-kit merge` read no verdict.
- A scheduled job (`cronjob_manage`, `cronjob_create`) may be created, edited, paused, resumed, run, and removed by any bot. The guard scans only a job's `script` and `command`, which run without a model, with the same code rules as `execute_code`. The `prompt` and every other field are prose or settings for a later model turn, whose tool calls the guard checks when they run, so they are not scanned.
- When another bot's message starts a bot's turn, its first text of the turn, before any tool call, is one short line to the owner saying what it received and what it is doing; the guard injects that reminder (a context under 900 characters, ending with the bot-to-bot terse-English rule that OPERATING.md and the dispatch, bootstrap, and chief skills repeat verbatim) for a message from a bot on this machine, and only the model's compliance, not code, makes it true.
- A unit has no GitHub issue. Its pull request carries the `faker-kit` label, applied by the session that opens it (the launch footer says so for both backends) and never by the coordinator; `add-project`, `install`, and `refresh` only make sure the label exists in each project's repository, and no existing pull request is backfilled. Autonomous bot paths (the babysit wake gate and agent, review and CI fixes, and `faker-kit merge --pr N` without `--owner-approved`) act only on labeled pull requests: the merge refuses an unlabeled one, or one whose labels it cannot read, before it judges any evidence, and `status` marks each line `labeled` or `unlabeled`. Owner-requested merges (`--owner-approved`, `--open`, `--all-projects`, `--match`) need no label and keep their author rules. The brief is the cloud session's first message and the pull request is the only GitHub artifact; the bot's progress lives in its orchestrate store under `~/.hermes/faker-kit/briefs/<bot>/`.
- Integrations poll or connect outbound. A public endpoint is allowed only if it verifies the sender's signature on every request, and it only wakes the bot's own agent job: Hermes's webhook platform checks GitHub's HMAC.
- `faker-kit refresh` runs for the owner, the chief, and the bootstrap bot, never a project bot; `install`, `runner`, `projects`, and `host` stay the owner's alone: once `~/.hermes/faker-kit/host-secret` exists (`install` and the first `host update` create it), `install`, `projects`, `host`, and `runner build|up` run only for a caller that pipes that secret on stdin with `--secret-stdin`, whatever its environment says, and every other caller gets the same `request_refused`; `runner slot`, which a kit service runs with no way to pipe a secret, keeps the profile-less rule (`host status|update|reload|rotate --json` is the Pal app's machine surface, one JSON envelope each, never a command line in its text). `faker-kit add-project` reports a project set up only after a signed ping to each webhook route it configured came back 2xx (`webhooks_live`).
- The first commit of an empty repository goes in only through `faker-kit import` (bootstrap bot, registered project, verified empty private repository of the chosen numeric id), run on the Mac by the pinned `hermes/lib/faker_kit_import.py` from a descriptor `import prepare` wrote. The helper pushes one root commit without force; the guard keeps no empty-repository exception for raw pushes or API writes, and scans the `device` tool's `shell.run` command like a terminal command. The helper excludes secrets, signing material, machine-local and build files, and GitHub automation by a fixed policy, and refuses links, nested git folders, special files, and unsafe git configuration. A client cannot lock a remote against other writers: the guarantee is that GitHub creates the ref once, the push has no force, and the loser is refused.
- Secrets never go in the repo, logs, argv, or URLs.
- A pull request merges only through `faker-kit merge` on its exact head, never on text a person or agent can edit into a comment.

## Paved paths

One way for each concern. Use it; do not add a second.

- **GitHub reads in `faker-kit`:** `Gh.page` / `Gh.json` (conditional ETag requests). Never shell out to a GraphQL-backed `gh issue`/`gh pr` subcommand in code a cloud session runs; use `gh api` REST calls.
- **Starting a cloud agent:** `faker_kit_cloud.Cloud.start(repo, command, workdir)`, reached through `faker-kit launch --brief-file`. A Claude Code session's task is its first message, a process argument, so it must never hold a secret; `CloudCommand.sensitive` is the only channel for one, sent on stdin or as a follow-up message, never in argv.
- **Starting a T3 Code thread:** `faker-kit launch --brief-file` under the `t3code` dispatch backend (`faker_kit_t3code.T3CodeLauncher`), which prints the one `mcp__t3code__t3_thread_launch` call and writes a prepared launch; the guard's `t3code.py` passes that call once. A bot never makes a T3 launch call that `launch` did not print.
- **Writing a state file:** write a sibling temp file, then `replace` it, with mode 600 for anything holding a key.
- **Time:** take `now` as a parameter (`self.now`), so tests control it; never call `time.time()` inside a decision.
- **A secret the owner provides:** the owner puts it in the bot profile's `.env` from their own terminal. Code reads it from the environment and redacts it from every log and error.

## Review guidelines

The Claude review workflow reads this section with REVIEW.md.

- Treat the rules in REVIEW.md as the review checklist, and every rule under Blocking in REVIEW.md as P1.
- Do not comment on anything the CI jobs above enforce: formatting, import order, lint findings, types, generated docs.
- Hermes invariants above are blocking: a merge by any route but `faker-kit merge`, a merge gate that skips CI on the exact head or counts a review, a rating, or a comment, a launch while the andon cord is pulled, or a secret reaching argv, a log, or a URL.

## Dispatch

`.agents/dispatch.json` and `.agents/dispatch.md` configure Hermes dispatch to cloud coding agents. Cloud sessions prove their work with the commands under Checks that their change affects and the `verify-faker-kit` skill (the `verification_skill`).

## Cloud sessions

A Claude Code cloud session (claude.ai/code, the Claude desktop and mobile apps, `claude --cloud`, `faker-kit launch`) starts from a clone of this repository. The cloud environment's setup script installs the toolchain once and the result is cached: `scripts/cloud-setup.sh` holds the same script for a clean container test (`docker run --rm -v "$PWD:/src:ro" ubuntu:24.04 bash -c 'cp -a /src /repo && cd /repo && bash scripts/cloud-setup.sh && node scripts/validate.mjs'`). The kit is not in this repository. The owner's cloud environment gets it from the end of its setup script and the `SessionStart` hook that script registers (`plugins/trust-ladder/skills/setup-cloud-agents/SKILL.md` step 2), so `/faker-mode` and every kit skill resolve with no plugin install; plugin hooks do not run there.

| Surface | Proof in a cloud session | Where the rest is verified |
|---|---|---|
| Kit plugins, hooks, scripts, the `faker-kit` command, the guard | the `hermes-e2e` and `kit-e2e` commands under Checks: the two e2e runs write JSON transcripts with stable digests to `artifacts/`; quote the digests and failing steps in the pull request | `claude plugin validate .` and the real-CLI plugin install step run in CI's `agents-load-the-kit` job |
| Hermes bots on a live machine | The hermes e2e transcript | The `verify-faker-kit` skill on the owner's Hermes machine |

- The owner wants pstack and trust-ladder skills available in every Hermes profile, the chief and project bots included, set up by the kit's machine config.
- The kit has no unit tests at all: behavior is proven only by end-to-end runs through real entry points that write a repeatable artifact (a JSON transcript and a stable digest); never add unit tests.
- The owner wants the kit to follow poteto's workflow from the upstream plugin repository in `upstream/source.json`, with Claude Code cloud in place of the upstream editor's cloud agents and Hermes bots in place of Grok Bot, at parity with that Grok Bot setup: features it has (the chief of staff, incident alerts from Sentry, PagerDuty, Datadog, and Grafana, per-push security, Slack, andon) stay; vendored plugins and repository setup match upstream (pstack from its Claude Code build `harness/pstack/claude-code/` with its own orchestrate playbook, the full upstream editor team kit kept as team-workflows, teaching included; no lint packs, no generated check script or CI wiring, no per-language best-practices skills); kit docs reuse the vendored upstream documentation (pstack guide, plugin READMEs) instead of restating it; bloat skills, scripts, and docs are proposed to the owner for removal first, never removed unasked. - The owner wants poteto's bug-report loop: a collaborator with write access adds the `faker:fix` label to a GitHub issue, the bot starts a cloud agent that reproduces the bug and either opens a PR that fixes and closes the issue or comments that it could not reproduce it, and the normal merge gate applies; an unlabeled issue is never acted on.

## Learned Workspace Facts

- The Hermes desktop app runs Bot Chat in its own backend process (a child of Hermes.app), separate from the launchd `ai.hermes.gateway` service; after reinstalling the kit, quit and reopen the app (restarting the gateway is not enough) for guard or plugin changes to take effect.
- One Hermes process serves several profiles and names the routed profile in a ContextVar (the `hermes_constants` HERMES_HOME override); plugin code that hops threads must use `contextvars.copy_context().run`, or the profile reads as `default`.
- In a routed Hermes turn, a command's environment gets only the bot `.env` names declared in `terminal.env_passthrough`, and Hermes never passes `GH_TOKEN`/`GITHUB_TOKEN` to commands; faker-kit reads what it needs from the bot profile's `.env` itself (`hermes/lib/faker_kit_env.py`), and `gh` in bot commands falls back to the machine's keyring login.
- `hermes cron run <id>` runs the job inline (an agent job as a full model turn), not on the next scheduler pass as its help says. Hermes runs a `--no-agent` cron script only from the profile's own `scripts/` folder, with `HERMES_HOME` set to that profile but without `~/.hermes/bin` on `PATH`; faker-kit job scripts call the wrapper by its absolute path. Hermes keeps only the last 50 output files per cron job and `hermes cron runs` lists no output, so counting output files does not show new runs and a 1-minute job's notices are gone within an hour.
- Hermes has a built-in webhook platform (`hermes webhook subscribe`, `platforms.webhook` in `~/.hermes/config.yaml`) that verifies GitHub HMAC signatures and can fire an existing cron job per event (`--cron-job`); the CLI validates `--cron-job` against the default profile's jobs even with `--route-profile`, while the gateway fires the job in the routed profile at runtime.
- Hermes loads extra skill folders from `skills.external_dirs` in each profile's own `config.yaml`, per profile; the kit's machine config `skills` list sets it for the default profile and every kit bot. `install.sh` writes each bot's `SOUL.md` as its role prompt followed by the shared `hermes/profiles/OPERATING.md` operating guide (Grok Bot's ideas in the kit's own words, never the leaked prompt text), so bots pick up guide changes only after a reinstall. A long-running Bot Chat keeps the skill text it loaded earlier; skill changes reach it only if it reloads the skill.
- The Claude Code kit plugins install from the `faker-kit` marketplace; trust-ladder depends on cli-for-agent and fails to load if that plugin is disabled. `claude plugin update` skips a plugin whose version did not change (bump trust-ladder's version when it changes), so a stale plugin cache needs a reinstall. The `claude` CLI on this machine is logged in only with `CLAUDE_CONFIG_DIR=~/.claude`, and its folder-trust entries live in `~/.claude/.claude.json`; `faker-kit add-project` and every launch mark the launch checkout trusted in the config the launch uses (`$CLAUDE_CONFIG_DIR/.claude.json`, or the older `.config.json` where it exists), so a launch stops on the "trust this folder" prompt only when that config is missing or unreadable. Claude Code crashes with `EINVAL: invalid argument, kqueue` when its stdin is redirected from `/dev/tty`, so open it on the terminal it already has. Several Claude Code sessions exiting together each save their own copy of `~/.claude/.claude.json` and the last one wins, which can drop a trust entry; the next launch writes it again.
- The GitHub repository is `tsnAnh/faker-kit` (renamed from team-kit; GitHub redirects the old name), a private repo on GitHub Free: branch protection, rulesets, and GitHub auto-merge are unavailable (HTTP 403), so merge gates are enforced in `faker-kit merge` code. The owner's Mac is never a CI runner: repositories on the owner's personal account run CI and the review workflow on GitHub-hosted `ubuntu-latest`, and `TitoniumLab` organization repositories use that organization's own self-hosted runners (`gh api orgs/TitoniumLab/actions/runners`): CI and the review workflow on `[self-hosted, macOS, X64]` (the org's iMac, `caotins-iMac-2`), screenbuddy's deploy on `[self-hosted, charmeji-prod]`, because TitoniumLab's GitHub-hosted jobs fail to start on org billing. This Mac's machine config is `~/.hermes/faker-kit/machine.yaml` (`faker-kit install --config` keeps the copy that `install.sh` and `faker-kit runner up` reuse), since `.agents/hermes-machine.yaml` still has `CHANGE-ME` webhook placeholders the loader refuses.
- claude-code-action skips with "workflow validation" on a PR that adds or changes its own workflow file; it runs only once the workflow matches the default branch (the review job skips; the security job still ran). The security job gets Claude's PASS/FAIL verdict as `--json-schema` structured output from the action, not a file Claude writes, and a missing verdict fails the job. In it, Claude Code refuses a `gh api ... -f body='<long multi-line text>'` command even when it matches an allowed `:*` prefix rule; write the body to a file and pass `-F body=@<file>` with an exact allowed command. GitHub's pull request `mergeable` is null until GitHub computes it, so treat null as unknown and recheck; GitHub rejects a label description over 100 characters with HTTP 422, which fails `faker-kit add-project`'s label creation.
- The kit's bot commands run on any Python 3.9+ using the vendored pure-Python PyYAML in `hermes/vendor` (a Homebrew `python3` upgrade once broke every bot command). Homebrew's default `python3` on this Mac is 3.14 without ruff or mypy; run the `lint` commands with a Python 3.12 environment that has the check tools on `PATH`. The ratchet (`scripts/agent-checks/ratchet.mjs`) counts only git-tracked files, so a suppression in a new untracked file passes locally and fails CI; `git add` new files before running them.
- Hermes keeps each profile's chat history in `~/.hermes/profiles/<bot>/state.db` (`sessions` and `messages` tables); read it to see what a bot actually said. A bot's `message_agent` may reach any agent; the default Hermes agent has browser and computer-use tools and no faker-kit guard.
- The upstream plugin repository ships `harness/pstack/claude-code/` (an official generated Claude Code build of pstack); trust-ladder is the owner's own plugin with no upstream counterpart. `pstack:faker-agent` matches upstream's stock agent: it reads the `faker-mode` skill's `SKILL.md` by path instead of running `/faker-mode`, so its spawn prompt needs no `/faker-mode` prefix; pass the absolute `SKILL.md` path in the brief.
