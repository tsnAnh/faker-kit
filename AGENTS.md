# AGENTS.md

This repository is faker-kit, a kit of agent skills for Claude Code. Read [README.md](README.md) for what it offers. This file tells an agent how to change it.

## Layout

- `plugins/<name>/` for every name in `upstream/source.json`: vendored from the upstream repository in `upstream/source.json`. Byte-identical to upstream except the rules in `upstream/model-map.json`, `upstream/compat-patches.json`, and `upstream/renames.json`, plus generated `.claude-plugin/plugin.json` and `agent-hooks/` files. A plugin named in `pluginSources` in `upstream/source.json` is read from that subdirectory instead of its own folder; pstack comes from upstream's generated Claude Code build, `harness/pstack/claude-code/`, so rules name its files by that path.
- `upstream/agent-hooks/hook-adapter.mjs`: runs a vendored plugin's upstream hooks from Claude Code hooks. The sync script copies it into each plugin that has a `hooks/hooks.json`.
- `plugins/trust-ladder/`: this repo's own plugin. Skills, templates, and helper scripts.
- `hermes/`: the Hermes module, this repo's own. The bootstrap, project, and chief bots' skills, profiles, guard plugin, the one `faker-kit` command, scheduled jobs, and `install.sh`. It loads only in Hermes bots, never in a coding agent, so it is not a plugin. Its skills follow the trust-ladder naming rules but need no `docs/catalog.json` entry, and must not reuse a plugin skill's name. See `hermes/README.md`.
- `docs/`: the kit's own pages (install, set up a repository, roll out, correct an agent, Hermes dispatch, the trust ladder, engineers' start page). `docs/README.md` indexes them and links into the vendored pstack guide (`plugins/pstack/docs/guide/`) and the plugin READMEs instead of restating them. `docs/reference/skills.md` is generated from `docs/catalog.json` and each SKILL.md.
- `scripts/`: `sync-upstream.mjs`, `validate.mjs`, and the generators and test runners.

## Never edit vendored files by hand

A hand edit under a vendored plugin fails `node scripts/sync-upstream.mjs --check`. To change a vendored file:

1. Model names: add or adjust a rule in `upstream/model-map.json`. Set `count` to the exact number of replacements.
2. A file that cannot load in Claude Code without an edit: add a rule to `upstream/compat-patches.json` (same shape) and say why in the rule id.
3. A name the team chose over upstream's: add a path or text rule to `upstream/renames.json`.
4. An upstream hook event the adapter does not map yet: add it to `UPSTREAM_TO_AGENT_EVENT` in the sync script and to the adapter, with a step in `scripts/e2e/kit-e2e.mjs` that runs the adapter on that event.
5. Anything else: change the behavior in `plugins/trust-ladder/` (a wrapper skill, hook, or template), not in the vendored file.
6. Run `node scripts/sync-upstream.mjs --src <checkout of the upstream repository>` or without `--src` to clone it. The clone retries transient failures; `SYNC_UPSTREAM_RETRY_SCALE` (0 to 1) only shortens its delays and wall bound, for the e2e steps.

To take a newer upstream: `node scripts/sync-upstream.mjs --ref <sha>`. Fix any rule whose count changed, then read `upstream/CHANGES.md` in the diff.

## Writing trust-ladder skills

- `name` equals the directory name: lowercase letters, digits, single hyphens.
- `description` says what the skill does and when to use it, in under 1024 characters.
- Write for an agent reading the file cold. Say which tool does what using the vocabulary in `plugins/trust-ladder/references/compat.md`.
- Never reuse a vendored skill's name. A project links skills by bare name, so a repeated name collides.
- If a vendored skill already covers the capability, use it (wrap it if the team needs more) instead of writing a second trust-ladder skill.
- Add every new skill to `docs/catalog.json` (layer, audience, an example prompt), then run `node scripts/gen-catalog.mjs`. `validate.mjs` fails on a skill without an entry.

## Checks

There is no single check command. CI runs these jobs in parallel (`.github/workflows/ci.yml`), and the commands below are the whole list:

| CI job | Commands |
|---|---|
| `lint` | `node scripts/agent-checks/ratchet.mjs check`, `node scripts/agent-checks/import-boundaries.mjs`, `node scripts/agent-checks/rule-fixtures.mjs`, `ruff check`, `mypy` |
| `validate` | `node scripts/sync-upstream.mjs --check`, `node scripts/validate.mjs`, `node scripts/gen-catalog.mjs --check` |
| `commit-messages` | `node scripts/check-commit-messages.mjs` |
| `hermes-e2e` (four matrix jobs) | `python3 hermes/e2e/run_dispatch_e2e.py --shard K/4 --artifact artifacts/hermes-e2e-K.json`; the whole suite in one command is `python3 hermes/e2e/run_dispatch_e2e.py --artifact artifacts/hermes-e2e.json` |
| `agents-load-the-kit` | `claude plugin validate .`, `node scripts/e2e/kit-e2e.mjs --artifact artifacts/kit-e2e.json` |
| `check` | no commands: the aggregate that needs `lint`, `commit-messages`, and every `hermes-e2e` job and fails if any did not succeed; keep it, the merge gate and this file name it |

The tools are `node`, `bun`, `jq`, `git`, `python3`, and `pip install ruff mypy types-PyYAML pyyaml`. Run the commands your change can affect, and `git add` new files first because the ratchet counts only tracked files:

- `hermes/` or `.agents/dispatch*`: `hermes-e2e`, then `lint`.
- `plugins/trust-ladder/`, `scripts/`, `docs/`, `upstream/`: `validate`, `kit-e2e`, then `lint`.
- A commit: `check-commit-messages`.

Each e2e run writes a JSON transcript to `artifacts/` and prints a digest that is the same on every run. The Hermes run starts one worker process per scenario (as many at a time as CPUs, `--jobs N`), each with its own temp home, stubs, and fixtures, and replays their `ok` lines in the order of the `SCENARIOS` table, so the digest of a whole run does not depend on timing. A scenario that needs another's state is one scenario (`owner-merge` runs four sections on one fixture). The driver's own `gh` and `hermes` stub calls run in-process (`--real-stubs` makes them real processes); every call a real entry point makes still spawns the stub. `--only a,b` runs some scenarios, `--list` names them, `--shard K/N` runs one balanced group (CI runs four, each on its own 2-vCPU runner, because the repository is private and a GitHub-hosted private runner has 2 vCPUs). A new scenario goes in `SCENARIOS` and in `hermes/e2e/budgets.json`, which holds each scenario's time budget in seconds (the slowest observed time, local and CI, times 1.5): the run fails when a scenario exceeds its budget, prints per-scenario and slowest-step times and writes them to the step summary, and `--budget-scale X` stretches the budgets for a slower machine.

The kit has no unit tests. Prove behavior with the e2e runs: add a step that drives the real entry point (a hook, a script, the `faker-kit` command, the guard plugin loaded as Hermes loads it) and records what it observed; never import internals and assert on them. The only other proof is `.agents/rule-fixtures.json` (real linters on good and bad inputs).

CI also runs what needs other toolchains, which a cloud session may lack:

```bash
claude plugin validate .                 # Claude Code marketplace schema
```

The commands above prove the code passes; the `verify-faker-kit` skill proves a user gets the behavior. Run the ones your change affects and the skill before reporting a change done.

## Hermes invariants

- A project bot is the long-lived coordinator chat for one repository. It decides what to launch and when to merge; no code state machine chooses for it. Code keeps only these gates: the guard's hard blocks (secret reads, repository deletion, push to main or force-push, raw `gh pr merge` and the merge API, wiping / or home, edits to the kit and the guard's own files; a scan limit is a hard block too: a command over 200,000 characters, more than 16 wrapper programs before the command, or `bash -c` scripts nested more than 3 deep are blocked with a reason naming the limit and never scanned in part, and code (`execute_code`, a scheduled job's script or command, `python3 -c` and the other interpreters) pushes only a literal named feature branch, never main, a refspec naming it, a branch built at run time, or a force, mirror, delete, or prune push), and `faker-kit merge` as the only way to land a pull request. Its gate is code: every check on the head passed and at least one check run that succeeded on it belongs to a `push` or `pull_request` workflow run of this head (a `pull_request` run must come from this pull request's branch in this repository, start after the pull request opened, and be attached to this pull request and its base branch, a `push` run must come from this repository and counts only when the head's `.github/workflows` folder equals the default branch's, and no pull request from that branch, in any state, may ever have targeted another base, and this pull request's base was never changed) of a workflow other than the review workflow and the kit-checks workflow (the repository's own GitHub Actions CI that builds and tests the pull request), no person has requested changes, the pull request is open, from this repository, against the default branch, and free of conflicts, and the merge is pinned to the head it checked. After the Kanban cutover (the marker `~/.hermes/faker-kit/kanban-cutover.json` exists) a `faker-kit merge` without `--owner-approved` also needs the card gate: the pull request's body begins with `Unit: <id>` and the card for `faker-kit:<project>:<id>` on board `default` exists, is open, is assigned to the calling bot, is bound to this pull request, the board is external, and Kanban is readable (an unreadable board refuses with `could not read Kanban` and merges nothing). It runs in the locked section after the cord and label checks and before the CI evidence, on every `--wait` poll, so a card closed or reassigned mid-wait refuses on the next poll; `--owner-approved` skips it and reads no Kanban. One writer: before the marker the loop JSON and `units.tsv` are the record and no Kanban call is made; once it exists Kanban cards on board `default` are the only writer and the old files are read-only history. A card completes only through Pal's `fleet-ci` rule (the CI evidence of the exact head, a `pr_acceptance` receipt), never locally and never forced: a merge or `faker-kit loop reconcile` records `pr_published` and `pr_merged` evidence and asks Pal to complete, and a refusal leaves the card open and is reported once. The kit never holds a claim between passes: `complete_card` claims (an `external:<bot>` lock Kanban reclaims after its claim TTL and gives up on after two stale reclaims), adds `pr_published` and `pr_merged` (and a part's stage evidence from its `Stage` lines) for that claim's own run only, never by copying rows from another run, and on a refusal releases the claim with `hermes kanban reclaim`, which leaves the card `ready` and resets Kanban's failure counter, so a refused card is retried on the next pass and never reaches `blocked` through the kit; recording stage evidence releases its claim the same way. A card found `blocked` after Kanban gave up on a stale `external:<bot>` claim is listed by `loop reconcile` as `stale_blocked` with the `hermes kanban unblock <id>` line for the owner or chief, never run by the kit. `faker-kit loop reconcile` (chief and project bots) reads GitHub for every recorded pull request and keeps the record following it with no bot message needed (merged goes through the completion rule above, closed unmerged becomes `abandoned`, a read that fails changes nothing and is listed `unreadable`, a part whose outcome is `built`, `installed`, or `verified` waits for its stage evidence), idempotent and fail closed; `loop digest` runs it first; the loop gate script stays read-only. `faker-kit launch` checks the backend's prerequisite before it starts anything (`claude` installed and signed in, or the `t3code` project resolving) and a refusal names only that backend's recovery. `faker-kit handoff --outcome` and `loop set --evidence` record what done means for a part. Faker-kit never calls Kanban's dispatch, daemon, swarm, specify, decompose, or `complete --force`, and never changes the board's `dispatch_mode`. Card bodies are readable ticket text above a machine-field footer, regenerated on every kit edit (an edit that changes nothing is not sent), and the parser reads both layouts; `faker-kit loop backfill --dry-run|--apply` rewrites old-layout cards with edit calls only, `faker-kit loop close <unit|card id|key> --reason TEXT [--as abandoned|folded|superseded|duplicate|junk]` archives a stray card without completing it, and `loop migrate --dry-run` and `loop backfill --dry-run` list `stray_cards` and never close them. Runs, jobs, check runs, and statuses of the review workflow are ignored: they neither pass nor block a merge, and no review, `Risk:` rating, or verdict is read. The `--owner-approved` flag stays on the command for the owner's request; the bot merges only when the owner asked, and no code checks that. With the flag the merge goes ahead over pending checks, failed checks, a failed or missing CI run, and a repository with no CI workflow, still pinned to the exact head, and prints each bypassed gate (each failed or pending check by name, and "no CI") in `bypassed`; it still refuses the andon cord, a conflict, a pull request that is not open, from this repository, and against the default branch, a person's requested changes, and the branch and base evidence checks, and its refusals say what to do next. An approval covers only the message that gave it; nothing stores it. The owner's own words reach a project bot also through the chief bot, only as a message from the chief carrying a line `Owner said (verbatim):` with the owner's message quoted whole, and only for clearing that project's own andon cord and for owner decisions on that project; the bot copies the quote into its store first, reads the cord back after a clear, and never takes a relay as merge approval, hold release, a launch the owner did not decide, or another project's cord (an instruction in the dispatch skill, not code; the transport cannot prove the quote is the owner's). `--wait <seconds>` (0 to 1800, default 0) waits inside the same call, polling every 30 seconds with fresh evidence, only while the head's checks are pending and none failed (with `--owner-approved` too: it waits first, then bypasses what is left); a failed check ends it at once, a head that moved refuses it, and the bound passing with checks still pending refuses with the time waited. The owner never retypes numbers: `--open` (every open non-draft pull request of one project), `--all-projects` (the chief only, every project on the machine) and `--match <text>` (open non-draft pull requests whose title or branch has the text) choose the targets, but only among pull requests opened by the GitHub login this machine's `gh` is signed in as (read once per call with `gh api user`, compared case-insensitively; unreadable refuses and merges nothing); another author's pull request is never merged by them and is listed under `skipped_not_owner` (`project`, `number`, `title`, `author`), `--match` counts only the machine login's candidates, and a call with no eligible pull request exits non-zero; `--pr N` merges whoever the author is and adds `author` and `named_by_owner` when it is not the machine login, run only with `--owner-approved`, are refused with `--pr` and without the flag, and send each pull request through the same `land` gate in ascending order; `--wait` defaults to 600 seconds there, shared by the whole call (a pull request the budget does not reach is reported `not attempted`), and several `--match` candidates merge nothing and exit 3 with `ambiguous`; `--pr N` is never replaced. `faker-kit launch` also refuses while the andon cord is pulled. The andon stop rule is an instruction in the skills, not code. No separate session checks a pull request before a merge: a bot lands a pull request through `faker-kit merge` when the owner asks or when its gates pass, and the author's own session may run the project's verification skills. `faker-kit status` and `faker-kit merge` read no verdict.
- Work shows on its card (after the cutover): `faker-kit launch` for a project bot refuses a unit (the brief file name) with no open unit card, naming `faker-kit loop unit <unit> --part <id>`, refuses a unit card that is already running, blocked, or closed (one session per unit), and after the session starts claims the card itself (`--ttl 28800`, the session id as `--session`) and writes the run id on the card's `Run:` field; an agent never runs `claim`. A part card is never claimed: Pal refuses a claim while its unit (prerequisite) cards are open, so its status stays Pal's and its `Work:` field and Status text say which unit runs, written by `loop set`, `launch`, `loop reconcile`, and `loop align --dry-run|--apply` (which never creates, archives, or completes a card). `loop reconcile` (project bot) claims a live unit card (open `Unit:` pull request, `Run:` or Session line) that is `ready`; every close releases its claim with `reclaim --reason`, and a merge completes it on the open run. `faker-kit loop check` prints one finding per card that does not show the work (live but not running, a claim within 30 minutes of expiry, a card Kanban gave up on after stale claims with its `hermes kanban unblock <id>` line the kit never runs, a merged pull request not done with its last `pr_acceptance` classification, a part inconsistent with its units) with the card id, what it saw, and the fix, exits 4 when one needs action, and heartbeats a live unit claim with under two hours left (Pal's heartbeat has no `--ttl`, so the kit sets `HERMES_KANBAN_CLAIM_TTL_SECONDS=28800` on that call); the babysit gate runs it every tick and adds one line only when a finding needs action, and the digest includes its lines. `--evidence built|installed|verified=<one line>` builds the payload from the text, the part's pull request head, and the version, device, or sha256 the text names; hand-written JSON is still validated.
- Pickup of ready unit cards (after the Kanban cutover): Pal's dispatcher cannot start workers on the external board `default`, so the kit does it with no new job, interval, or daemon. When `faker-kit pickup` reads on, the babysit gate tick (every webhook wake and the hourly tick, no model turn) runs `faker-kit pickup status --no-job` and prints `Ready card to pick up: <unit> (card <id>)` once per card and wakes the bot, never claiming, launching, or writing a card itself; the bot writes the brief from the card and runs `faker-kit launch`, which claims the card. `pickup_candidates` (`hermes/lib/faker_kit_pickup.py`) is the one rule: Kind `unit`, the bot's own project and assignee (so a chief card, a part card, or another project's card is never selected, whatever its age), status `ready`, not archived or closed, no pull request, `Session` line, or `Run`, an `Owner decisions:` line other than `none recorded` and a goal line longer than the title, and no steer; oldest first. While pickup is on, `Kit.launch_card` refuses a unit when it would exceed `max_in_flight` of `.agents/dispatch.json` (default 2) running unit cards for the project or `max_in_flight_total` of `guard.yaml` (default 4) in total, naming the running cards and free slots; the gate lists at most the free slots. The stop switch is one command: `faker-kit pickup off|on|status`, state in `~/.hermes/faker-kit/pickup.json` (atomic, world readable, written only by this command, absent means off, so install and refresh leave it off); `on` and `off` run only for the owner and the chief, a project bot reads `status` (enabled, since, by, the babysit job id and next run, candidates per project). The andon cord still stops every launch. A unit whose session was steered once and an hour later still has no pull request is blocked by `loop reconcile` while pickup is on: the claim is released with `reclaim`, then `hermes kanban block --kind needs_input` with a reason naming the unit; never forced, completed, or unblocked, reported to the owner once, never picked up or relaunched. `loop check` lists a ready unit card that is only a title or has no decisions as `needs_brief` (not needing action). Workers never merge (only `faker-kit merge`), never force a card (no `--force` call exists), and the andon cord is the bot's own rule.
- Unit cards follow GitHub with no model turn: the babysit gate (`settle_cards` in `hermes/cron/scripts/faker-kit-babysit-gate.py`, every webhook wake and tick) runs `faker-kit loop reconcile`, which reads GitHub for each bound unit card and settles it through `CardSettler` (merged completes through `complete_card`, closed unmerged is abandoned and its claim released, an open non-draft pull request records `pr_published` on the open run once per head, never claiming and never forced). The gate never reads the webhook payload, creates a card, or binds a pull request (unbound ones stay for `loop check`), and prints one line per card and head only for a refusal or an unreadable pull request, tracked in `gates/<bot>/faker-kit-babysit-settle.json`.
- A project bot tells the chief of staff that a pull request of a chief unit opened, merged, closed, or needs the owner through code, never `message_agent` (a cron or webhook wake has none, and the Bot Chat hop cap refuses it): the babysit gate runs `faker-kit news`, dedupes by pull request, kind, and (for `needs the owner`) head in `~/.hermes/faker-kit/chief-news/<bot>.json`, and fires the no-agent `faker-kit-chief-news` job, which delivers the lines to `bot-chat:<chief>`; a note is sent once its run reads `ok`, otherwise it is retried on the next event wake, and a failure never fails the babysit wake. That job has a 2099 one-shot schedule and runs only when the gate fires it; there is no polling job and no chief webhook, and `gateway.bot_loop_guard.max_hops` stays as set.
- A cloud session's closing summary reaches a project bot only through GitHub, read-only: `faker-kit launch` appends one rule to every brief (both backends, once) that a session posts a pull request comment whose first line is exactly `Closing summary:` (Done, Skipped, Open questions, Blockers) before it ends, and that a session that cannot finish a pull request opens a draft one whose body begins with `Unit: <unit-id>` and carries the same summary; "ready, never draft" applies to a pull request the session finished, and a draft is a hold no bot merges. `faker-kit session summary <unit-id|pr-number> [--dry-run]` reads the pull request and the latest `Closing summary:` comment by its author or the machine login through `Gh`, prints it wrapped as untrusted data (secret shapes redacted, cut at a fixed length) with `source`, `readable`, and the head's check counts, and stores it in the unit's own card text as `Session summary (a claim, not proof):` with the head it was read at (the same summary at the same head edits nothing; `--dry-run` writes nothing; a project bot stores only its own project's unit cards). It never writes to the session or GitHub, runs `claude`, reads a secret, or completes or merges anything: the summary is a claim, and GitHub (pull request, head, checks, artifact) decides. The babysit gate adds one line to a wake for a unit whose pull request opened, went to draft, merged, or closed at a head it has not asked about, and never wakes for it alone. `faker-kit session steer <unit-id> --session <id>` is the only `claude` call in this flow: for a unit with no pull request after its timebox it sends one message asking for the closing summary or the draft pull request, records it in the card first, and never sends a second.
- A scheduled job (`cronjob_manage`, `cronjob_create`) may be created, edited, paused, resumed, run, and removed by any bot. The guard scans only a job's `script` and `command`, which run without a model, with the same code rules as `execute_code`. The `prompt` and every other field are prose or settings for a later model turn, whose tool calls the guard checks when they run, so they are not scanned.
- When another bot's message starts a bot's turn, its first text of the turn, before any tool call, is one short line to the owner saying what it received and what it is doing; the guard injects that reminder (a context under 900 characters, ending with the bot-to-bot terse-English rule that OPERATING.md and the dispatch, bootstrap, and chief skills repeat verbatim) for a message from a bot on this machine, and only the model's compliance, not code, makes it true.
- A unit has no GitHub issue. Its pull request carries the `faker-kit` label, applied by the session that opens it (the launch footer says so for both backends) and never by the coordinator; `add-project`, `install`, and `refresh` only make sure the label exists in each project's repository, and no existing pull request is backfilled. Autonomous bot paths (the babysit wake gate and agent, review and CI fixes, and `faker-kit merge --pr N` without `--owner-approved`) act only on labeled pull requests: the merge refuses an unlabeled one, or one whose labels it cannot read, before it judges any evidence, and `status` marks each line `labeled` or `unlabeled`. Owner-requested merges (`--owner-approved`, `--open`, `--all-projects`, `--match`) need no label and keep their author rules. The brief is the cloud session's first message and the pull request is the only GitHub artifact; the bot's progress lives in its orchestrate store under `~/.hermes/faker-kit/briefs/<bot>/`.
- Integrations poll or connect outbound. A public endpoint is allowed only if it verifies the sender's signature on every request, and it only wakes the bot's own agent job: Hermes's webhook platform checks GitHub's HMAC.
- `faker-kit refresh` runs for the owner, the chief, and the bootstrap bot, never a project bot; `install`, `runner`, `projects`, and `host` stay the owner's alone: once `~/.hermes/faker-kit/host-secret` exists (`install` and the first `host update` create it), `install`, `projects`, `host`, and `runner build|up` run only for a caller that pipes that secret on stdin with `--secret-stdin`, whatever its environment says, and every other caller gets the same `request_refused`; `runner slot`, which a kit service runs with no way to pipe a secret, keeps the profile-less rule (`host status|update|reload|rotate --json` is the Pal app's machine surface, one JSON envelope each, never a command line in its text). `faker-kit add-project` reports a project set up only after a signed ping to each webhook route it configured came back 2xx (`webhooks_live`).
- The first commit of an empty repository goes in only through `faker-kit import` (bootstrap bot, registered project, verified empty private repository of the chosen numeric id), run on the Mac by the pinned `hermes/lib/faker_kit_import.py` from a descriptor `import prepare` wrote. The helper pushes one root commit without force; the guard keeps no empty-repository exception for raw pushes or API writes, and scans the `device` tool's `shell.run` command like a terminal command. The helper excludes secrets, signing material, machine-local and build files, and GitHub automation by a fixed policy, and refuses links, nested git folders, special files, and unsafe git configuration. A client cannot lock a remote against other writers: the guarantee is that GitHub creates the ref once, the push has no force, and the loser is refused.
- Secrets never go in the repo, logs, argv, or URLs.
- A pull request merges only through `faker-kit merge` on its exact head, never on text a person or agent can edit into a comment.

## Paved paths

One way for each concern. Use it; do not add a second.

- **Kanban calls in `faker-kit`:** every `hermes kanban` call goes through `hermes/lib/faker_kit_kanban.py`; nothing else shells out to it.
- **GitHub reads in `faker-kit`:** `Gh.page` / `Gh.json` (conditional ETag requests). Never shell out to a GraphQL-backed `gh issue`/`gh pr` subcommand in code a cloud session runs; use `gh api` REST calls.
- **Starting a cloud agent:** `faker_kit_cloud.Cloud.start(repo, command, workdir)`, reached through `faker-kit launch --brief-file`. A Claude Code session's task is its first message, a process argument, so it must never hold a secret; `CloudCommand.sensitive` is the only channel for one, sent on stdin or as a follow-up message, never in argv.
- **Starting a T3 Code thread:** `faker-kit launch --brief-file` under the `t3code` dispatch backend (`faker_kit_t3code.T3CodeLauncher`), which prints the one `mcp__t3code__t3_thread_launch` call and writes a prepared launch; the guard's `t3code.py` passes that call once. A bot never makes a T3 launch call that `launch` did not print.
- **Writing a state file:** write a sibling temp file, then `replace` it, with mode 600 for anything holding a key.
- **Time:** take `now` as a parameter (`self.now`), so tests control it; never call `time.time()` inside a decision.
- **A secret the owner provides:** the owner puts it in the bot profile's `.env` from their own terminal. Code reads it from the environment and redacts it from every log and error.

## Review guidelines

The Claude review workflow reads this section with REVIEW.md.

- Treat the rules in REVIEW.md as the review checklist, and every rule under Blocking in REVIEW.md as P1.
- Do not comment on anything the CI jobs above enforce: formatting, import order, lint findings, types, generated docs.
- Hermes invariants above are blocking: a merge by any route but `faker-kit merge`, a merge gate that skips CI on the exact head or counts a review, a rating, or a comment, a launch while the andon cord is pulled, or a secret reaching argv, a log, or a URL.

## Rules and what enforces them

`/correct` keeps this table. Drop a rule once its mistake can no longer happen.

| Rule | Enforced by |
|---|---|
| Vendored plugins match upstream plus the rules | `sync-upstream.mjs --check` in CI's `validate` job |

## Dispatch

`.agents/dispatch.json` and `.agents/dispatch.md` configure Hermes dispatch to cloud coding agents. Cloud sessions prove their work with the commands under Checks that their change affects and the `verify-faker-kit` skill (the `verification_skill`).

## Cloud sessions

A Claude Code cloud session (claude.ai/code, the Claude desktop and mobile apps, `claude --cloud`, `faker-kit launch`) starts from a clone of this repository. The cloud environment's setup script installs the toolchain once and the result is cached: `scripts/cloud-setup.sh` holds the same script for a clean container test (`docker run --rm -v "$PWD:/src:ro" ubuntu:24.04 bash -c 'cp -a /src /repo && cd /repo && bash scripts/cloud-setup.sh && node scripts/validate.mjs'`). The kit is not in this repository. The owner's cloud environment gets it from the end of its setup script and the `SessionStart` hook that script registers (`plugins/trust-ladder/skills/setup-cloud-agents/SKILL.md` step 2), so `/faker-mode` and every kit skill resolve with no plugin install; plugin hooks do not run there.
