# Set up a project and run its bot's commands

`faker-kit add-project` creates a project bot for one repository: its profile, its agent job, the andon label, and the launch checkout Claude Code sessions start from. The bot then runs `faker-kit launch`, `merge`, `status`, `andon`, `incidents`, and `issues`.

## Sub-features

- `bot-launch`: `launch` starts a cloud session with the brief as its first message, on the `--model` and `--effort` the bot chose for the task (the model is the account default without `--model`; the effort is capped at `high`: `xhigh` or `max` is lowered to `high` and printed as `effort_lowered`, and no `--effort` starts at `high` and prints `effort_defaulted`), refuses a model or effort the claude CLI does not take, refuses a brief that does not start with `/faker-mode`, one outside the bot's briefs folder, a secret in a brief, a vendored kit that is not this machine's, and any launch while the andon cord is pulled.
- `bot-status`: `status` prints one gate line per open pull request, with its `updated` time, naming `unit <id>` when the pull request body's first line is `Unit: <id>`, whoever authored it, ending each line with its gate (`ready to merge` or `blocked: <reason>`), and nothing else from the body.
- `bot-merge`: `merge` refuses on failed or pending checks, a head whose only passing checks are the review workflow's own jobs or the kit-checks workflow's (or a check run that names no other workflow run, or whose workflow run came from `workflow_dispatch`, `pull_request_target`, `workflow_run`, another commit, another repository, another pull request, another base branch, a fork, a run created before the pull request opened, or a branch that is not this pull request's or ever targeted another base), a missing or older-head approval, `Risk: high` or no Risk line, a failed, missing, or forged `security-review` (the linked review-workflow run on the head has no successful `security` job), a change to a workflow, guard, or protected path, a person's changes-requested review, a fork, and a conflict; on the first call that passes every gate it merges the exact head at once, with no owner message and no wait; a mergeable value GitHub has not computed yet is re-read for about twenty seconds before it refuses. In a repository without the review workflow yet, `status` and `merge` report `security-review` as not reported instead of failing.
- `bot-incidents`: `incidents` polls checks, health URLs, and Sentry, PagerDuty, Datadog, and Grafana alerts with tokens from the bot's `.env`, lists each new incident once, and a triage session launches from the brief template. No job runs it: the owner asks the bot, and `add-project` creates no incidents job.
- `bot-bug-reports`: `issues` lists an issue only when a collaborator with write access added its `faker:fix` label; a fix session launches from the brief template; `add-project` creates the three labels.
- `bot-wake-gates`: the `faker-kit-babysit` job (which also handles bug reports; there is no issues job) carries a gate script that runs `faker-kit issues` and `faker-kit status` on each tick and skips the model turn with `{"wakeAgent": false}`. With no open pull request, no listed issue, and no `faker-kit notice:` line it is always quiet (no first-run wake, no heartbeat) and only records the empty status, so the next pull request counts as a change. Otherwise it wakes the agent for a listed issue, a notice, no earlier tick, changed status lines (each pull request line carries `updated <time>`, so a comment or review changes it), six hours since the last wake while a pull request is open, or a previous run after the last wake that did not finish ok, read from `hermes -p <bot> cron list --all` (`Last run:`), at most three wakes in a row for a failed run (`retries`; any other wake resets it, and a heartbeat or a real change still wakes at the cap). A last run that cannot be read (listing fails, job absent, unparsable time, no `hermes`) is quiet, with nothing on stderr and nothing written. It keeps `{fingerprint, woke_at, retries}` under `~/.hermes/faker-kit/gates/<bot>/faker-kit-babysit.json`; a command failure, a wrong shape, or a missing wrapper exits non-zero and writes nothing, so the agent wakes with a Script Error. The chief's `faker-kit-loop` job has a stateless gate that runs `faker-kit loop --all` and wakes only for a due waiting part or a `to_report` part. `install` and `add-project` remove the retired `faker-kit-issues`, `faker-kit-security`, and `faker-kit-incidents` jobs and their kit-owned gate scripts and state from a project bot, and no other job.
- `bot-andon`: `andon raise` and `clear` for the project, and the machine cord read at launch.

## How to get to it (user POV)

- The owner runs `faker-kit add-project OWNER/REPO` (or asks the bootstrap bot, or runs `/setup-hermes-project`).
- The project bot runs `faker-kit <command>` from its Hermes profile; its jobs run the same skill.

## Driving it

`python3 hermes/e2e/run_dispatch_e2e.py --artifact <path>`. Proof: every "launch", "merge", "window", and andon step prints `ok`, so do the babysit gate, loop gate, "last run", "retries", "add-project removes the retired", and "install removes the retired" steps for `bot-wake-gates`, and two runs print the same digest. The "guard:" steps are the guard's verdicts through the real plugin (each call's verdict is in the transcript's `verdicts`), the "runner" steps are the CI slots, and the "vendor" steps are `faker-kit vendor` and `vendor_kit.py`.

## Gotchas

- Without `HERMES_HOME` set to the bot's profile, `faker-kit` refuses project commands: it only runs them as a project bot.
- The stubs answer only the calls the e2e models. A command that needs another call fails loudly; extend the stub the way the real CLI answers, not to make the proof pass.
