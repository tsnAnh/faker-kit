# Set up a project and run its bot's commands

`faker-kit add-project` creates a project bot for one repository: its profile, its agent job, the andon and `faker-kit` pull request labels, and the launch checkout Claude Code sessions start from. The bot then runs `faker-kit launch`, `merge`, `status`, `andon`, `incidents`, and `issues`.

## Sub-features

- `bot-launch`: `launch` starts a cloud session with the brief as its first message, on the `--model` and `--effort` the bot chose for the task (the model is the account default without `--model`; the effort is capped at `high`: `xhigh` or `max` is lowered to `high` and printed as `effort_lowered`, and no `--effort` starts at `high` and prints `effort_defaulted`), refuses a model or effort the claude CLI does not take, refuses a brief that does not start with `/faker-mode`, one outside the bot's briefs folder, a secret in a brief, and any launch while the andon cord is pulled.
- `bot-source-import`: `faker-kit import prepare` (bootstrap bot only) binds a registered project, its canonical repository and numeric id, an absolute source path, the signed-in login, the installed kit commit, and the helper's hash into a descriptor and prints one `mac_command`; it refuses a wrong id, name, visibility, permission, sign-in, source path, or any remote with a branch, tag, or commit. The Mac command delivers `hermes/lib/faker_kit_import.py` at that commit, checks its hash, and imports one root commit of a snapshot that leaves out secrets, signing files, local and build files, and workflows; retries and a lost reply return the recorded commit, a competing writer is refused, and `import verify` checks the remote against the receipt. Proof: the `import:` steps of the e2e run and the `device` groups of `guard-calls.json`. Not proven by the run: a live GitHub repository or the real Mac and its device shell tool.
- `bot-t3code-launch`: a repository whose `.agents/dispatch.json` says `backend: t3code` (with a valid `t3code` object) gets no cloud session from `launch`: it runs every brief, flag, and andon check, writes an owner-only prepared launch named for the sha256 of the final message under `launches/<bot>/`, and prints the one `mcp__t3code__t3_thread_launch` call (project, `Unit: <unit-id>` title, a worktree from `origin/<default branch>` unless `base_ref` says otherwise, the `dispatch.json` model, the message). An unknown backend, an unreadable `dispatch.json`, and a missing or invalid `t3code` object refuse; no `dispatch.json` or `backend: claude` keeps the cloud path. The guard passes that call once, only for the printed message from the bot that ran `launch`, within an hour, with every argument as printed; it refuses a replay, an edited message, an added or changed argument, an expired, future-dated, or another bot's prepared launch, and the T3 tools that merge, fork, hand off, link, or change projects; thread reads arrive wrapped as untrusted.
- `bot-session-summary`: every launch (cloud or `t3code`, once even for a brief that already holds it) appends the closing summary rule: a `Closing summary:` pull request comment (Done, Skipped, Open questions, Blockers) before the session ends, or a draft pull request whose body begins with `Unit: <unit-id>` and holds the summary. `session summary <unit-id|pr-number> [--dry-run]` reads, read-only, the pull request and its latest `Closing summary:` comment by the pull request's author or the machine login (a stranger's is ignored; a draft's body or a body's marker line is the fallback), prints the text wrapped as untrusted data with secret shapes redacted and cut at 2000 characters plus `source`, `readable`, and the head's check counts (`no pull request` is `no readable summary`), and stores it in the unit's own card text as `Session summary (a claim, not proof):` with the head (the same summary at the same head edits nothing; `--dry-run` makes no card, GitHub, or `claude` call). The babysit gate adds one `Closing summaries to read:` line to a wake for a unit whose pull request opened, went to draft, merged, or closed at an unasked head, and stays silent otherwise. `session steer <unit-id> --session <id>` asks a session of a unit with no pull request once, recorded in the card before the one `claude -p --cloud` call.
- `bot-status`: `status` prints one gate line per open pull request, with its `updated` time, naming `unit <id>` when the pull request body's first line is `Unit: <id>`, whoever authored it, an explicit `labeled` or `unlabeled` token after draft or ready, ending each line with its gate (`ready to merge` or `blocked: <reason>`), and nothing else from the body. An unlabeled pull request, or one whose labels are absent or malformed, never reads `ready to merge`: its gate is `blocked: not labeled faker-kit; autonomous bots leave it alone, only the owner merges it`. Every open pull request is still listed.
- `bot-merge`: `merge` refuses on failed or pending checks, a head whose only passing checks are the review workflow's own jobs or the kit-checks workflow's (or a check run that names no other workflow run, or whose workflow run came from `workflow_dispatch`, `pull_request_target`, `workflow_run`, another commit, another repository, another pull request, another base branch, a fork, a run created before the pull request opened, or a branch that is not this pull request's or ever targeted another base), a missing or older-head approval, `Risk: high` or no Risk line, a failed, missing, or forged `security-review` (the linked review-workflow run on the head has no successful `security` job), a change to a workflow, guard, or protected path, a person's changes-requested review, a fork, and a conflict; without `--owner-approved` it first refuses a pull request that lacks the `faker-kit` label, or whose `labels` field is absent or malformed, naming the label and saying only the owner merges it, before it reads any evidence and again on every `--wait` poll (a label removed mid-wait refuses), while `--owner-approved`, `--open`, `--all-projects`, and `--match` skip the label check; on the first call that passes every gate it merges the exact head at once, with no owner message and no wait; a mergeable value GitHub has not computed yet is re-read for about twenty seconds before it refuses. In a repository without the review workflow yet, `status` and `merge` report `security-review` as not reported instead of failing.
- `bot-conflict-follow-up`: `session conflicts [--dry-run]` walks the project's open pull requests that are labeled `faker-kit`, come from this repository, begin with a `Unit: <id>` line, and whose unit card is the bot's and bound to them (anything else is listed with its reason and never read in detail). It reads each one's `mergeable` and `mergeable_state` first and no check, re-polls an unknown state (three reads, two five-second pauses, then gives up without calling it clean), and for a conflicting one, draft or ready, whatever its checks say, sends the unit's recorded session one `claude -p --cloud` message (merge the base into the existing branch, resolve, rerun checks, push, no new pull request) and records `Conflict follow-up: head <sha> <time>` in the card first, so a second run, tick or webhook storm sends nothing, a new conflicting head gets one more follow-up, and a head still conflicting 45 minutes after its follow-up, a third conflicting head, a unit with no session or a failed delivery is `tell-owner`. `--dry-run` sends and writes nothing. The babysit gate runs it after `loop reconcile` on every tick with no model turn, prints one line per `tell-owner` once per head, and a tick that only sent follow-ups wakes nothing. Proof: `hermes/e2e/session_conflicts_scenario.py` and the `conflict gate:` steps of `wake_gate_scenario.py`. Fake only: a real `claude -p --cloud` delivery and GitHub's lazy `mergeable` need the live machine.
- `bot-pr-label`: `add-project`, and `install` and `refresh` for every already registered project (configured or not), create the `faker-kit` label with `--force` in the project's repository, so a second run changes nothing; a repository the login cannot label does not fail `install`, and its entry in the JSON `refreshed` list carries `labels: unavailable: <reason>`. `launch` appends the label rule to every brief on both backends (add the label when opening the pull request, check it before ending, add `Label: faker-kit` to the body, never label a pull request the session did not open). No existing pull request is labeled.
- `bot-incidents`: `incidents` polls checks, health URLs, and Sentry, PagerDuty, Datadog, and Grafana alerts with tokens from the bot's `.env`, lists each new incident once, and a triage session launches from the brief template. No job runs it: the owner asks the bot, and `add-project` creates no incidents job.
- `bot-bug-reports`: `issues` lists an issue only when a collaborator with write access added its `faker:fix` label; a fix session launches from the brief template; `add-project` creates the three labels.
- `bot-wake-gates`: the `faker-kit-babysit` job (which also handles bug reports; there is no issues job) carries a gate script that runs `faker-kit issues` and `faker-kit status` on each tick and skips the model turn with `{"wakeAgent": false}`. It counts only `labeled` pull request lines: `unlabeled` ones are dropped from the fingerprint, the wake decision, and the lines shown to the agent, and when only unlabeled ones are open it behaves as for no open pull request (including the single last-gone wake); a line it cannot classify is kept. With no open pull request, no listed issue, and no `faker-kit notice:` line it is always quiet (no first-run wake, no heartbeat) and only records the empty status, so the next pull request counts as a change. Otherwise it wakes the agent for a listed issue, a notice, no earlier tick, changed status lines (each pull request line carries `updated <time>`, so a comment or review changes it), six hours since the last wake while a pull request is open, or a previous run after the last wake that did not finish ok, read from `hermes -p <bot> cron list --all` (`Last run:`), at most three wakes in a row for a failed run (`retries`; any other wake resets it, and a heartbeat or a real change still wakes at the cap). A last run that cannot be read (listing fails, job absent, unparsable time, no `hermes`) is quiet, with nothing on stderr and nothing written. It keeps `{fingerprint, woke_at, retries}` under `~/.hermes/faker-kit/gates/<bot>/faker-kit-babysit.json`; a command failure, a wrong shape, or a missing wrapper exits non-zero and writes nothing, so the agent wakes with a Script Error. The babysit gate also runs `faker-kit news` and, for each new `opened`, `merged`, `closed`, or `needs the owner` event of a chief unit's pull request, fires the no-agent `faker-kit-chief-news` job (2099 one-shot, delivers to `bot-chat:<chief>`, never created without a chief bot), marking a note sent only when that run's last run reads `ok` and otherwise retrying it on the next event wake with one wake line the first time. The chief's `faker-kit-loop` job has a stateless gate that runs `faker-kit loop --all` and wakes only for a due waiting part or a `to_report` part. `install` and `add-project` remove the retired `faker-kit-issues`, `faker-kit-security`, and `faker-kit-incidents` jobs and their kit-owned gate scripts and state from a project bot, and no other job.
- `bot-kanban-cutover`: `faker-kit loop migrate --dry-run` (chief and project bot) reads the board, the loop JSON, `units.tsv`, and GitHub, prints what would become cards (open parts and units, skipped closed ones, unmapped entries, the `reconcile` counts), and makes no write call and no marker. `--apply` refuses unless board `default` is external, creates each card once by idempotency key, links each unit as a prerequisite of its part card, resumes after an interrupted run, and writes `~/.hermes/faker-kit/kanban-cutover.json` only after every card exists; a project bot cannot apply before the chief. Fake only: proof is the `kanban:` migrate steps of `hermes/e2e/kanban_scenario.py` against a fake `hermes`; real Pi is not available here, so a live Kanban board is not proven.
- `bot-card-text`: every card body the kit writes is readable ticket text (summary, handoff line, owner decisions, pull request links, sessions, status) then a machine footer line and the fields; the parser reads the old fields-on-top layout too and an edit rewrites it in the new one; text is built only from the card, ledger, `units.tsv`, and the unit's brief (never GitHub text) with token-like values withheld; an edit that changes nothing sends no call. `loop backfill --dry-run|--apply` rewrites existing cards with edit calls only (archived cards included; a card with no source is listed `no_source`), `loop close` archives a stray card with its kind and reason in History and refuses an empty or token-like reason, another role's or project's card, an already closed card, and a card with a recorded pull request unless `--as superseded|folded`; `loop migrate --dry-run` and `backfill --dry-run` list `stray_cards`; `loop migrate` skips the `units.tsv` header row, folded, superseded and taken-back rows, and a unit id listed twice, reporting `skipped_rows`. Proof: the `kanban text:`, `kanban backfill:` and `kanban close:` steps of `hermes/e2e/kanban_text_scenario.py`, and the old-layout step of `kanban_scenario.py`. Fake only.
- `bot-card-refs`: every card made by `loop unit` and `handoff` gets a reference `<PREFIX>-<n>` (the project's next number from 1, counted over archived cards too, never padded; the prefix table is the code defaults `PREFIXES` in `hermes/lib/faker_kit_refs.py` plus the machine registry `card-prefixes.json`, which `add-project` and a project's first card fill with a derived unique prefix; an unreadable registry refuses naming the file) in the footer `Ref:` field and a title `<REF> <phrase>` the creating bot writes with `--title` (an empty, unit-id or slug-like title is refused with the flag and an example); the body is a ticket with Goal, Done means, Current status and Owner decisions; `loop show <REF>` resolves any case and leading zeros and names `owner` and `route_to` for another project's card, `loop close`, `loop title` and `session` commands refuse another project's reference with `<REF> belongs to the <bot> bot; ask that bot`; `loop backfill --refs --dry-run|--apply` writes only the `Ref:` footer line of open cards that have none, in creation order (done, merged and archived cards are skipped as `not open`; their numbers still count for the next card) (body and title byte-identical, edit calls only, a second apply changes nothing).
- `bot-one-writer`: before the marker no Kanban call is made and the old loop JSON and `units.tsv` are the record; after it `handoff`, `loop`, `loop set`, `loop digest`, and `loop unit` read and write the cards, a write to the old loop JSON is refused, the project bot may only `show`, `migrate`, `unit`, and `reconcile`, and no dispatch, daemon, swarm, specify, decompose, board change, `dispatch_mode` change, or forced completion call ever appears in the call log. Proof: the `kanban:` steps (handoff, loop, loop set, evidence, loop unit, the call-log step). Fake only.
- `bot-card-gate`: after the cutover `merge` without `--owner-approved` refuses a pull request with no `Unit: <id>` line, no card, a done or archived card, a card assigned to another bot, a card bound to another pull request, a non-external board, or an unreadable Kanban (`could not read Kanban`), after the cord and label checks, before CI evidence, and on every `--wait` poll; `--owner-approved` merges in each case without reading Kanban. Proof: the `kanban merge:` steps of `kanban_scenario.py`. Fake only.
- `bot-card-completion`: a merge or `loop reconcile` completes a unit or part card only through the fake Pal's `pr_acceptance` receipt (`pr_published` and `pr_merged` evidence, then `complete`, never forced); a pending, failed, stale, provenance, or mismatch receipt leaves the card `ready` with its claim released (`reclaim`), is reported once, and is retried on the next pass; evidence is written per run (never copied from a stale run); a card Kanban gave up on is reported `stale_blocked` with its unblock line. Proof: the `kanban merge:` and `kanban reconcile:` steps, the `kanban merge and reconcile:` step, and the `kanban claims:` steps of `run_dispatch_e2e.py`. Fake only: the real Pal acceptance is not proven here.
- `bot-reconcile`: `loop reconcile` (chief and project bot, and first inside `loop digest`) sets a merged pull request's part or unit merged, a closed unmerged one `abandoned`, leaves an open one alone, lists an unreadable one under `unreadable` and changes nothing for it, keeps a `built`, `installed`, or `verified` part open as `awaiting stage evidence`, and a second run changes nothing; before the cutover it writes only the chief's loop JSON and a project bot's run only reports. Proof: the `kanban reconcile:` steps of `kanban_scenario.py` (before and after the cutover).
- `bot-launch-preflight`: `launch` checks the backend's prerequisite before it starts anything: `claude` needs the CLI installed and signed in, `t3code` needs its project settings to resolve; a refusal names only that backend's recovery, never the other backend, and starts no session and writes no prepared launch. Proof: the `launch preflight:` steps of `run_dispatch_e2e.py` and the `t3code:` refusal steps of `hermes/e2e/t3code_scenario.py`.
- `bot-outcomes`: `handoff --outcome merged-pr|built|installed|verified` records what done means, `loop set --evidence STAGE=REF` records the stage proof (a JSON object payload on a card), and a merged pull request does not finish a `built`, `installed`, or `verified` part without its evidence. Proof: the outcome steps of `run_dispatch_e2e.py` ("handoff --outcome", "a merged pull request does not complete a built part") and the `kanban:` evidence steps of `kanban_scenario.py`.
- `bot-quiet-wake`: the babysit and chief loop gates wake only for a changed pull request line (more than its `updated` time), a blocker, a completion, a notice, an issue, the six-hour heartbeat while a pull request is open, or a failed previous run (at most three in a row); the gates are read-only and never call `loop reconcile`. Proof: `hermes/e2e/wake_gate_scenario.py`, run by `run_dispatch_e2e.py`.
- `bot-card-events`: the babysit gate runs `loop reconcile` every tick with no model turn, so a merged unit card completes through Pal, a closed unmerged one is abandoned with its claim released, an open non-draft pull request records `pr_published` once per head on the open run, nothing is written on a repeat, a refusal or unreadable pull request prints one line once per card and head, and an unbound pull request is left for `loop check`. Proof: the `card events` steps of `hermes/e2e/wake_gate_scenario.py` and `kanban_scenario.py`. Fake only: real Pal acceptance and a real webhook wake need the live Pi.
- `bot-card-visibility`: after the cutover `launch` refuses a unit with no open card (naming `faker-kit loop unit <unit> --part <id>`) or one already running, and claims the card itself (ttl 28800, the session id, a `Run:` field); `loop reconcile` claims live ready unit cards and `loop close` releases; part cards are never claimed and show their running units in `Work:` text (`loop set`, `loop align --dry-run|--apply`, idempotent); `loop check` reports the five finding classes with fixes, exits 4 when action is needed, and extends near-expiry claims; the babysit gate adds one line only then; one-line `--evidence built|installed|verified=<text>` builds the payload. Proof: the `visibility` steps of `hermes/e2e/kanban_visibility_scenario.py` and the `card check gate` step of `wake_gate_scenario.py`. Fake only: Pal's real claim, heartbeat TTL env, and run fields are not proven here.
- `bot-hot-load`: `add-project`, `host reload` and `reload_routes` load a project's webhook routes into the running gateway with no restart: the kit writes the route entries (literal secret, mode 0600, marked `managed_by: faker-kit`) to `webhook_subscriptions.json` by an atomic rename under Hermes's own lock file, keeps the static config write, and polls the local listener with the signed ping; the output says `loaded: hot`, or `loaded: restart (hot path failed: <ping result>)` when the ping stayed 404 or unanswered and the owner's shell restarted the gateway as the fallback (a bot's turn says `no (hot path failed: ...)` and leaves the restart to the owner). A stale kit route is dropped from the file with the static prune, entries the kit did not write are never touched, and a rerun writes nothing. Proof: the `hot-load` steps of `hermes/e2e/webhook_hot_load_scenario.py` (a fake of Pal's reader) and the `host reload` steps of `run_dispatch_e2e.py`. Live: only on the owner's Pi (a gateway started before `add-project` answers the new routes with 2xx and `loaded: hot`, and Pal's real reader accepts the kit's entries).
- `bot-andon`: `andon raise` and `clear` for the project, and the machine cord read at launch.
- `environment-kit`: a cloud session gets the kit from the owner's environment, never from the repository. The setup phase (`scripts/environment-setup.sh`) writes `faker-kit-install.sh` and registers it once as a `SessionStart` hook in `settings.json` (honouring `CLAUDE_CONFIG_DIR`). With `FAKER_KIT_READ_TOKEN` set, the hook fetches the kit, links every kit skill and subagent into the config folder, and prints exactly the compat block (`plugins/trust-ladder/references/compat.md`) on stdout. A second run is a no-op, an existing skill that is not a link is kept, and with no token the hook logs and exits 0 with nothing installed. `launch` reads no kit from the repository.

## How to get to it (user POV)

- The owner runs `faker-kit add-project OWNER/REPO` (or asks the bootstrap bot, or runs `/setup-hermes-project`).
- The project bot runs `faker-kit <command>` from its Hermes profile; its jobs run the same skill.

## Driving it

`python3 hermes/e2e/run_dispatch_e2e.py --artifact <path>`. Proof: every "launch", "merge", "window", and andon step prints `ok`, so does every "t3code" step (`bot-t3code-launch`: the prepared launch, the printed call, the refusals, and the "t3code guard" verdicts through the real plugin), so do every "kanban", "kanban merge", and "kanban reconcile" step (`bot-kanban-cutover`, `bot-one-writer`, `bot-card-gate`, `bot-card-completion`, `bot-reconcile`; fake `hermes` only, no real Pi), the "launch preflight" steps, so do the babysit gate, loop gate, "last run", "retries", "add-project removes the retired", and "install removes the retired" steps, and the "chief-news", "chief's Bot Chat", "delivers nothing", "delivery job", and "receipt" steps for `bot-wake-gates`, and two runs print the same digest. The "guard:" steps are the guard's verdicts through the real plugin (each call's verdict is in the transcript's `verdicts`), the "runner" steps are the CI slots, and the "environment-setup.sh" section is `environment-kit`: the hook registered once, the skills linked and the compat block printed with a token, the second run a no-op, a kept non-link skill, and the no-token exit.

## Gotchas

- Without `HERMES_HOME` set to the bot's profile, `faker-kit` refuses project commands: it only runs them as a project bot.
- The stubs answer only the calls the e2e models. A command that needs another call fails loudly; extend the stub the way the real CLI answers, not to make the proof pass.
- `bot-pickup`: `faker-kit pickup status|on|off` (off by default, state in `pickup.json`; `on` and `off` only for the owner and the chief). While on, the babysit gate prints `Ready card to pick up: <unit> (card <id>)` once per ready, workable unit card of the bot (never a chief, part, other project's, pull-request, session, run, steered, or title-only card), at most the free slots (2 per project, 4 in total, or `max_in_flight` and `max_in_flight_total`), and `launch` refuses past them naming the running cards; a unit steered once with still no pull request is blocked by `loop reconcile` after releasing its claim, reported once. `loop check` lists a title-only ready unit as `needs_brief`. Proof: `hermes/e2e/pickup_scenario.py` and the `pickup gate:` steps of `hermes/e2e/wake_gate_scenario.py`. Live: only on the owner's Pi (merge, refresh, `pickup status` reads off, restart, `pickup on`, restart, status reads enabled with the job's next run, then one ready workable unit card is picked up).
- `bot-ready`: `faker-kit loop ready [--dry-run]` (project bots only; the chief and the bootstrap bot are refused) marks a draft unit pull request ready for review through GitHub's GraphQL call when it is open, from this repository, labeled `faker-kit`, begins `Unit: <id>`, its card is open, the bot's and bound to it and not blocked, the session finished (a `Closing summary:` comment at or after the head commit, or no live run) and every check passed under the merge gate's own evaluation; it re-reads the head before the write, never merges, and a second run prints `unchanged`; the babysit gate runs it after `loop reconcile` with no model turn and prints `marked #n ready for review (unit <id>, head <short>)`; `merge` refuses a draft with one sentence, and `--pr N --owner-approved` marks it ready first (`marked_ready: true`); `loop check` lists a draft still open 30 minutes after its session finished; the launch footer tells sessions to open ready. Proof: `hermes/e2e/ready_scenario.py` and the `ready gate:` steps of `hermes/e2e/wake_gate_scenario.py`. Live: only a real GraphQL flip on a real draft pull request on the owner's machine (`loop ready --dry-run` first).
