# Project bot scheduled jobs

`faker-kit add-project` creates these jobs in each project bot's profile from this file: each `##` heading is the job name, and its schedule, delivery, skill, and prompt come from the lines under it. `{bot}` becomes the bot's profile name. Edit them here, then run `hermes/install.sh` again; it creates missing jobs and rewrites each job's schedule and prompt in place, so a job keeps its id and its paused or active state. Jobs start active when `gh` is signed in on this machine (or the bot has a `GH_TOKEN`) and start paused otherwise; running `faker-kit add-project OWNER/REPO` again resumes them. `add-project --heartbeat-every` replaces the default schedule. Times are in the profile's `timezone`, Asia/Ho_Chi_Minh. When the machine config names a Slack channel for the bot, every job also delivers to it through Hermes's native Slack platform.

Every job is an agent job: a model turn in the bot's own profile with the named skill loaded and the prompt as its task. The bot decides what to do through faker-mode's playbooks; the guard's hard blocks and `faker-kit merge`'s gate still apply. A job may carry a Script gate, a file under `hermes/cron/scripts/` that `install.sh` writes into the bot's `scripts/` folder; Hermes runs it before each tick and skips the model turn when the gate prints `{"wakeAgent": false}`, so a quiet tick costs no turn. The project job carries one, and so does the chief's `faker-kit-loop`; the gates share `faker_kit_gate.py` and `faker_kit_cron_list.py`, which `install.sh` writes beside them. `faker-kit-babysit` runs `faker-kit issues` and `faker-kit status` and goes quiet, with no first-run wake and no heartbeat, while no pull request is open, no issue is listed, and no `faker-kit notice:` line printed; the next pull request to open counts as a change. Otherwise it wakes the agent when an issue is listed, a `faker-kit notice:` line printed, the status lines changed since it last woke the agent (each pull request's line carries its `updated` time, so a new comment or review changes it), six hours passed since it last woke the agent while a pull request is open (`HEARTBEAT_SECONDS` in `faker_kit_gate.py`, not the job's schedule), or the job's previous run after that wake did not finish ok, read from `hermes -p <bot> cron list --all`. A gate that cannot read that run (Hermes missing, the listing failing, the job absent, an unparsable time) stays quiet, so a broken secondary signal never defeats the gate, and the six-hour heartbeat still bounds it. Failed-run wakes are capped: the gate counts them in `retries` and, at three in a row, stops waking for a failed run until the status changes, a notice or issue appears, or the heartbeat passes (any other wake resets the count). It records the fingerprint of the status lines, the wake time, and `retries` in `~/.hermes/faker-kit/gates/<bot>/faker-kit-babysit.json`, written when it wakes the agent and when the fingerprint of a quiet no-pull-request status changes; a state file without `retries` reads as 0. A gate that cannot read the project exits non-zero with a short message and writes nothing, so Hermes shows a Script Error and the agent wakes, as it did before gates. Each run sees the job's previous output, so it does not repeat itself. Hermes's webhook platform fires `faker-kit-babysit` on a pull request, review, check suite, or commit status event, and when a collaborator adds the `faker:fix` label to an issue, each through a route signed with the bot's secret (`faker-kit install --config`, or `faker-kit add-project` once a machine config is kept); the schedule is the fallback for a missed delivery, and its quiet ticks are skipped by the gate. `faker-kit install` and `add-project` remove the retired `faker-kit-issues`, `faker-kit-security`, and `faker-kit-incidents` jobs, and their gate scripts and gate state, from a project bot's profile; no other job is removed.

## faker-kit-babysit

Schedule: `every 1h`
Deliver: `bot-chat:{bot}`
Skill: `dispatch`
Script: `faker-kit-babysit-gate.py`
Prompt: `Babysit this project. Follow the Wake section of the dispatch skill. If a Script Error block is shown, the gate could not read the project: run faker-kit status and faker-kit issues yourself and go on; if either fails, tell this chat the error and stop. Otherwise the Script Output above is this tick's faker-kit issues and faker-kit status, so use the status as Wake step 1's status (run faker-kit status again only after you change a pull request's state) and the issues as the Bug reports section's step 1 output (do not run faker-kit issues again in this turn; faker-kit issues --claim is still yours). Then tell the chief what changed for its units (Wake step 2), drive each pull request that needs it to merge-ready with faker-mode's Babysit playbook, have a separate session verify the ones that are green, and land the verified ones with faker-kit merge. For each issue the Script Output lists, follow the Bug reports section of the dispatch skill: write a brief from the fix-issue template, start it with faker-kit launch on the model and effort the Choose the model section picks, and claim the issue with faker-kit issues --claim. A line that starts with `faker-kit notice` and a colon in any command's output or in the Script Output is never answered [SILENT]: say it to this chat as printed. Answer [SILENT] only when no notice printed, no issue was listed, and nothing needs the owner.`
