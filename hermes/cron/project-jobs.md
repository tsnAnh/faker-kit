# Project bot scheduled jobs

`faker-kit add-project` creates these jobs in each project bot's profile from this file: each `##` heading is the job name, and its schedule, delivery, skill, and prompt come from the lines under it. `{bot}` becomes the bot's profile name. Edit them here, then run `hermes/install.sh` again; it creates missing jobs and rewrites each job's schedule and prompt in place, so a job keeps its id and its paused or active state. A job is rewritten only when this file or the job's listed schedule or script differs from what the install last applied, which it records in `~/.hermes/faker-kit/jobs/<bot>.json`; a prompt edited only inside Hermes is not noticed, so delete that file to rewrite every job. Jobs start active when `gh` is signed in on this machine (or the bot has a `GH_TOKEN`) and start paused otherwise; running `faker-kit add-project OWNER/REPO` again resumes them. `add-project --heartbeat-every` replaces the default schedule. Times are in the profile's `timezone`, Asia/Ho_Chi_Minh. When the machine config names a Slack channel for the bot, every job also delivers to it through Hermes's native Slack platform.

Every job is an agent job: a model turn in the bot's own profile with the named skill loaded and the prompt as its task. The bot decides what to do through faker-mode's playbooks; the guard's hard blocks and `faker-kit merge`'s gate still apply. A job may carry a Script gate, a file under `hermes/cron/scripts/` that `install.sh` writes into the bot's `scripts/` folder; Hermes runs it before each tick and skips the model turn when the gate prints `{"wakeAgent": false}`, so a quiet tick costs no turn. The project job carries one, and so does the chief's `faker-kit-loop`; the gates share `faker_kit_gate.py` and `faker_kit_cron_list.py`, which `install.sh` writes beside them. `faker-kit-babysit` runs `faker-kit issues` and `faker-kit status`, counts only the status lines marked `labeled` (it drops each `unlabeled` pull request line, and treats a status with only unlabeled ones as `no open pull requests`), and goes quiet, with no first-run wake and no heartbeat, while no pull request is open, no issue is listed, and no `faker-kit notice:` line printed; the next pull request to open counts as a change. When the last open pull request merges or closes (the stored status held pull request lines and the status is now `no open pull requests`), it wakes the agent once with that reason and records the empty status, so the next tick is quiet again; it reads neither `units.tsv`, the ledger, nor Kanban, and it never calls `faker-kit loop reconcile`, so it wakes for any such change and the agent decides what to report. Otherwise it wakes the agent when an issue is listed, a `faker-kit notice:` line printed, a pull request's status line changed since it last woke the agent in more than its `updated` time (a line whose pull request, head, and gate text are unchanged and whose gate is not `blocked:` is healthy progress and wakes nothing, so a new comment or review on it is quiet), or a pull request left the status, six hours passed since it last woke the agent while a pull request is open (`HEARTBEAT_SECONDS` in `faker_kit_gate.py`, not the job's schedule), or the job's previous run after that wake did not finish ok, read from `hermes -p <bot> cron list --all`. A gate that cannot read that run (Hermes missing, the listing failing, the job absent, an unparsable time) stays quiet, so a broken secondary signal never defeats the gate, and the six-hour heartbeat still bounds it. Failed-run wakes are capped: the gate counts them in `retries` and, at three in a row, stops waking for a failed run until the status changes, a notice or issue appears, or the heartbeat passes (any other wake resets the count). Duplicate status lines collapse first (exact duplicates to one, several lines for the same `#N` to the last), and the fingerprint covers the collapsed lines. A changed-status wake prints only the lines of the pull requests that changed (a new or changed blocker included, once) and one `#N merged or closed` line for each pull request that was in the stored status and is gone; first, heartbeat, notice, issue, and failed-run wakes print every line. It records the fingerprint of the status lines, a per-pull-request fingerprint (`pulls`: the line, the line without its `updated` time, and whether the gate is `blocked:`), the wake time, and `retries` in `~/.hermes/faker-kit/gates/<bot>/faker-kit-babysit.json`, written when it wakes the agent and when the fingerprint of a quiet no-pull-request status changes (a first run with nothing open); a state file without `retries` reads as 0, and one without `pulls` reads as changed once. A gate that cannot read the project exits non-zero with a short message and writes nothing, so Hermes shows a Script Error and the agent wakes, as it did before gates. Each run sees the job's previous output, so it does not repeat itself. Hermes's webhook platform fires `faker-kit-babysit` on a pull request, review, check suite, or commit status event, and when a collaborator adds the `faker:fix` label to an issue, each through a route signed with the bot's secret (`faker-kit install --config`, or `faker-kit add-project` once a machine config is kept); the schedule is the fallback for a missed delivery, and its quiet ticks are skipped by the gate. `faker-kit install` and `add-project` remove the retired `faker-kit-issues`, `faker-kit-security`, and `faker-kit-incidents` jobs, and their gate scripts and gate state, from a project bot's profile; no other job is removed.

`faker-kit-chief-news` tells the chief of staff what happened to the pull requests of its units without `message_agent`, which a cron or webhook wake does not have, and without the Bot Chat hop counter. It is a `no-agent` script job delivering to the chief's Bot Chat (`bot-chat:{chief}`), created only when the machine has a chief bot (refresh prints `chief_news` when it has none), never on Slack. Its schedule is a one-shot in 2099, so it never fires on a timer: the babysit gate fires it with `hermes -p <bot> cron run faker-kit-chief-news`, and a manual run leaves that occurrence pending. Each babysit gate run calls `faker-kit news` (the pull requests of `units.tsv` rows whose origin is `chief`, and open pull requests whose `Unit:` line names one), decides `opened`, `merged`, `closed`, or `needs the owner` (open, not a draft, and its status line reads `ready to merge`), and drops what it already sent, keyed by pull request and kind (and head for `needs the owner`) in `~/.hermes/faker-kit/chief-news/<bot>.json`. A first run records merged and closed pull requests as already sent. It writes new lines there as pending, fires the job, whose script prints them, and marks them sent only when `cron list --all` shows that run's last run as `ok`; otherwise they stay pending for the next event wake, and the first time a failure is seen it wakes the babysit agent once with one line saying so. A news or delivery failure never fails the babysit gate.

## faker-kit-babysit

Schedule: `every 1h`
Deliver: `bot-chat:{bot}`
Skill: `dispatch`
Script: `faker-kit-babysit-gate.py`
Prompt: `Babysit this project. Follow the Wake section of the dispatch skill. If a Script Error block is shown, the gate could not read the project: run faker-kit status and faker-kit issues yourself and go on; if either fails, tell this chat the error and stop. Otherwise the Script Output above is this tick's faker-kit issues and faker-kit status, so use the status as Wake step 1's status (run faker-kit status again only after you change a pull request's state) and the issues as the Bug reports section's step 1 output (do not run faker-kit issues again in this turn; faker-kit issues --claim is still yours). If the gate woke because the last open pull request merged or closed, no pull request is open: run faker-kit loop reconcile, reconcile units.tsv (before the Kanban cutover; after it the unit cards are the record), and tell the chief the news for each chief unit whose pull request is gone (merged or abandoned), per Wake step 2, then answer. Run faker-kit loop reconcile once where you read the status (it reads GitHub and keeps the record current; before the cutover it only reports for a project bot), then tell the chief what changed for its units (Wake step 2), drive each labeled pull request (the status shows `labeled`; leave an `unlabeled` one alone) that needs it to merge-ready with faker-mode's Babysit playbook, have a separate session verify the ones that are green, and land the verified ones with faker-kit merge. For each issue the Script Output lists, follow the Bug reports section of the dispatch skill: write a brief from the fix-issue template, start it with faker-kit launch on the model and effort the Choose the model section picks, and claim the issue with faker-kit issues --claim. A line that starts with `faker-kit notice` and a colon in any command's output or in the Script Output is never answered [SILENT]: say it to this chat as printed. Answer [SILENT] only when no notice printed, no issue was listed, and nothing needs the owner.`
