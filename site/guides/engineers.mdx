This guide follows the order work happens in: understand, design, build, prove, review, land. Then it covers correcting agents, keeping the codebase healthy, and running many agents at once. Each section says which skill to use and gives a prompt to copy.

<Note>
Examples use Claude Code. In Codex, start a skill with `$` instead of `/`. In Pi, use `/skill:`. You rarely need the name: describe the task and the agent picks the skill.
</Note>

## How /faker-mode works

Most building work goes through `/faker-mode`. Say what you want and how you will know it is done. It picks a **playbook** that matches your words, hands work to subagents, runs your verification skill, and opens a pull request with evidence. It stays on for the session until you say "exit faker mode".

```text
/faker-mode add CSV export to the reports page. verify it really works.
```

You do not need to name the playbook. The tables below name it so you know what to expect. The full list is in [Playbooks and principles](/reference/playbooks).

## 1. Understand the code

| You want to | Run |
|---|---|
| Know how something works today | `/how is virtualization implemented?` |
| Know why it was built that way, or when it broke | `/why are we still stuck on an old version of node?` |
| Get a plain explanation, step by step | `/teach me how notifications get to a user's phone` |
| Restate the last answer without jargon | `/bro` |
| Pick up your own earlier work | `/recall the work i did yesterday on virtualization` |
| Take over another agent's work from a transcript, branch, or cloud URL | `/faker-mode pick up <branch or URL>` (Session pickup playbook) |
| Find what a change could break outside the diff | `/blast-radius this change to the session cache` |

## 2. Design before building

Pick by the shape of the decision:

| The decision is | Run |
|---|---|
| Types, signatures, and module structure | `/architect this first, and answer any open questions with prototypes` |
| Between a few options you could try | `/faker-mode prototype both approaches and show me` (Prototype playbook: throwaway code, a decision, then the real build) |
| Best settled by competing attempts | `/arena take my prompt to the arena verbatim` (several agents try it; the best parts are combined) |
| A large migration or multi-part change | `/figure-it-out`, or `/faker-mode plan this as small, verifiable PRs` (Multi-phase plan playbook) |
| Something with no precedent in the codebase | Say "exhaust the design space" to apply that principle |

Detail: [Design before building](/how-to/design-before-building) and [Plan with code](/explanation/plan-with-code).

## 3. Build

| The change is | Run | Playbook |
|---|---|---|
| New or changed behavior | `/faker-mode build this behind a feature flag. verify it really works.` | Feature |
| A bug, reproduced in the running app | `/faker-mode the export writes duplicate rows when a retry lands mid-run. repro first, then fix and verify.` | Bug fix |
| A bug where you want a failing test first | `/tdd reproduce the crash on an empty cart` | |
| A measured slowness | `/faker-mode startup got slow. trace it and fix it.` | Perf issue |
| One metric to improve over many rounds | `/faker-mode get the bundle under 300 KB` | Hillclimb |
| A live symptom: a leak, CPU spin, or glitch | `/faker-mode diagnose why the app uses CPU while idle` | Runtime forensics |
| A profile or trace file you already have | `/faker-mode read this cpuprofile and tell me what is slow` | Trace forensics |
| A structural change with no behavior change | `/faker-mode rename and extract ...` | Refactoring |
| A UI that must match a mockup or old version exactly | `/faker-mode make the settings screen match this mockup` | Visual parity |
| A new skill or prompt change | `/faker-mode write a skill for ...` | Authoring a skill, then Eval |

Related skills:

- **One concern done several ways** (dates, networking, logging): `/paved-path we have three ways to format dates` picks one approved way and migrates the rest.
- **Language idioms**: `/kotlin-best-practices`, `/swift-best-practices`, `/rust-best-practices`, `/python-best-practices`, `/dart-best-practices`, `/typescript-best-practices`.
- **A CLI that agents will run**: `/cli-for-agents`.

## 4. Prove it works

Tests alone are not proof. Every change a user can see needs evidence from the running app: screenshots, a recording, or a transcript.

| Situation | Run |
|---|---|
| The repository has a verification skill | Say "verify it really works", or `/verify-this the list no longer jitters when scrolling` |
| It has none yet | `/create-verification-skill` ([how](/how-to/build-a-verification-skill)) |
| The app is Android, iOS, Flutter, or KMP | `/control-mobile` first, then `/create-verification-skill` |
| The app is web, an IDE, or Electron | `/control-ui` |
| The app is a CLI or TUI | `/control-cli` |
| You only need Playwright smoke tests | `/run-smoke-tests` |
| You only need compile and type checks | `/check-compiler-errors` |

Why this matters most: [Verification is all you need](/explanation/verification-is-all-you-need).

## 5. Clean up and review

| You want to | Run |
|---|---|
| Remove AI-generated clutter from the branch | `/deslop` |
| Remove comments that explain a workaround instead of fixing it | `/no-comments` |
| Cut machine-sounding prose from a PR description | `/unslop` |
| Audit security and correctness | `/thermos review this branch` (two reviews in parallel) |
| Review maintainability only | `/thermo-nuclear-code-quality-review` |
| Have several models challenge the approach | `/interrogate review this pr.` |
| Review, test, commit, and open a PR in one pass | `/review-and-ship` |
| Make a PR easy for humans to review | `/make-pr-easy-to-review`, or `/pr-review-canvas` for an interactive walkthrough |

Every pull request also gets reviewed by Claude and Codex (set up with `/setup-review-bots`) and needs a human code owner's approval.

## 6. Land the pull request

| What is in the way | Run |
|---|---|
| No branch or PR yet | `/new-branch-and-pr` |
| CI is red, fix it now | `/fix-ci` |
| CI is red, keep watching until green | `/loop-on-ci` |
| Merge conflicts | `/fix-merge-conflicts` |
| Review comments to read | `/get-pr-comments` |
| All of the above until it is merge-ready | `/faker-mode babysit this PR until it is merge-ready` (Babysit playbook) |
| A green stack of PRs to land in order | `/faker-mode ship this stack` (Shipping playbook) |

Detail: [Build, review, and ship](/how-to/build-review-ship).

## 7. When an agent gets something wrong

Don't just fix it in chat. Make it stick:

| Situation | Run |
|---|---|
| A mistake you never want to see again | `/correct the agent keeps catching Exception and swallowing it` |
| You know it should be a lint rule or CI check | `/encode-lint-rule ban android.util.Log; use AppLog` |
| The same review bot finding shows up on two PRs | `/correct` it: it belongs in a check |
| Reviewers keep leaving the same comment | `/style-guide-from-reviews last 90 days`, then `/correct` each entry |
| A hard session you want to learn from | `/reflect that took too long. capture what we learned.` |
| You want agents to follow your personal style | `/automate-me` or `/workflow-from-chats` |
| AGENTS.md should keep learning from sessions | `/continual-learning` |

`/correct` picks the strongest layer that can hold the rule, proves it fails on a bad example and passes on a good one, and logs it in `.agents/corrections.tsv`. Detail: [Correct an agent](/how-to/correct-an-agent) and [Capture lessons](/how-to/capture-lessons).

## 8. Keep the codebase healthy

| Situation | Run |
|---|---|
| A bad pattern is spreading | `/gardener what spread in the codebase this week?` |
| One concern is done several ways | `/paved-path` |
| Add linting for another stack | `/setup-lint-pack rust` (see [Lint packs](/reference/lint-packs)) |
| The verification skill has drifted from the app | `/maintain-verification-skill` |
| Replacing an internal API | Say "migrate callers, then delete the legacy API" |

Detail: [Garden the codebase](/how-to/garden-the-codebase).

## 9. Run many agents

First measure: `/trust-audit` tells you how many agents the repository can take today.

| Repository state | Safe number of agents |
|---|---|
| No verification skill, or `check` fails | 1 to 5, each watched |
| Every layer scores 2 or more | 10 to 30, in cloud sessions |
| Every layer scores 3, checks under 15 minutes, both review bots on | 100 or more |

Then pick by the shape of the work:

| The work is | Run |
|---|---|
| Many independent subtasks inside one task | `/swarm` |
| One long task to run until a condition holds | `/faker-mode i'm stepping away. migrate every caller to the new async store.` (Autonomous run) |
| A queue of independent PRs, each carried to merged | `/faker-mode autopilot these issues` (Autopilot-full) |
| A queue delivered as one stack you land | Autopilot-stack playbook |
| A multi-day project with one coordinator | `/faker-mode orchestrate the store migration. i'll check in twice a day.` (Orchestrate) |
| Unattended work you want to audit later | `/show-me-your-work keep a decision trail i can review` |
| Work you need to stop and resume | `/faker-mode pause safely` |
| Recurring upkeep on a schedule | `/setup-routines` |
| Agents in parallel without your laptop | `/setup-cloud-agents` |
| Choosing models per role | `/setup-pstack`, or `/run-model` for one seat |
| Disk full of old worktrees and simulators | `/faker-mode clean up worktrees` |

Detail: [Run many agents](/how-to/run-many-agents) and [Scaling to many agents](/explanation/scaling-agents).

## Steer an agent mid-task

Say a principle's name in plain words to change how the agent works:

```text
attack the premise: two fixes for the flaky sync failed the same way
subtract before you add. delete the obsolete adapters first, then design what's left.
redesign from first principles as if offline mode was always a requirement
apply prove it works. run the real import flow and show me the written records.
```

All principles are listed in [Playbooks and principles](/reference/playbooks).
